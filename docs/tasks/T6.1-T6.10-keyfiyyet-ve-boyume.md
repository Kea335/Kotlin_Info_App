## T6.1 — Compose UI və naviqasiya testləri

**P1 · 2 gün · Branch:** `test/ui-axinlari`

### Problem

311 unit test biznes məntiqini qoruyur, amma ekranların özü yalnız əl ilə
yoxlanılır. Sprint 2 və 3-ün 16 qəbul bəndi («Don't keep activities», döndərmə,
RTL) iki aydır «cihazda baxılmayıb» kimi açıqdır — çünki hər dəfə əl ilə
təkrarlamaq bahadır. `androidTest`-də yalnız Room DAO testləri var (7 test).
CI-da emulyator job-u (`cihaz-testleri`) artıq işləyir.

### Addımlar

1. Asılılıqlar: `androidx.compose.ui:ui-test-junit4`, `ui-test-manifest` (debug),
   `androidx.navigation:navigation-testing`.
2. Test üçün `AppContainer`: `FakeCompiler`, yaddaşda DataStore və Room
   (`inMemoryDatabaseBuilder`) — testlər şəbəkəyə çıxmır və bir-birinə təsir etmir.
3. Axın testləri (hər biri bir istifadəçi ssenarisi):
   - Dərs aç → «Oxudum» → siyahıda tərəqqi artır
   - Nəzəri çalışma: düzgün və səhv cavab; səhv «Səhvlərim»ə düşür
   - Praktiki çalışma: `FakeCompiler` ok / səhv / oflayn — üç vəziyyətin görünüşü
   - Test turu: 15 sual → nəticə ekranı → statistika yenilənir
   - Axtarış: «istisna» → «İstisnalar» (T0.1-in UI səviyyəsində qıfılı)
   - Dil dəyiş (`en`) → başlıqlar ingiliscədir, tərəqqi yerindədir
4. State bərpası — `StateRestorationTester` ilə (B1-də əl ilə yoxlanan eyni
   ssenarilər): test turunun 7-ci sualı, redaktor mətni, çalışma indeksi və
   səviyyə filtri, açıq dialoq.
5. RTL smoke: `LocalLayoutDirection = Rtl` altında əsas ekranlar render olunur,
   kod bloku LTR qalır (semantics-dən `LayoutDirection` oxunur).

### Qəbul kriteriyası

- [ ] 6 axın testi + 4 bərpa testi + RTL smoke `connectedDebugAndroidTest`-də yaşıl
- [ ] Testlər şəbəkəyə çıxmır (fake kompilyator), ardıcıllıqdan asılı deyil
- [ ] CI-ın `cihaz-testleri` job-u 15 dəqiqədən uzun çəkmir
- [ ] T2.3, T2.4-ün «cihaz» bəndləri test adına istinadla bağlanıb

### Diqqət

Screenshot testləri (Roborazzi / Paparazzi) bu task-a daxil **deyil** — 15 dil
× 2 tema üçün etalon şəkillərin saxlanması ayrıca qərardır. Əvvəlcə davranış
testləri.

## T6.2 — Baseline Profile

**P1 · 1 gün · Branch:** `perf/baseline-profile`

### Problem

T2.6 soyuq başlanğıcı iki mərhələli yükləmə ilə qısaltdı, amma kod ilk
açılışda hələ də JIT ilə işləyir. Baseline Profile əsas yolları quraşdırma
vaxtı AOT kompilyasiya edir — Compose tətbiqlərində ilk açılış və ilk sürüşmə
üçün ən ucuz qazancdır.

### Addımlar

1. `:baselineprofile` modulu (`com.android.test` + `androidx.baselineprofile`).
2. Generator: tətbiqi aç → dərslər siyahısını sürüşdür → bir dərs aç və
   sürüşdür → çalışmalar və test tablarına keç.
3. `:app`-da `baselineProfile(project(":baselineprofile"))` və
   `androidx.profileinstaller`.
4. Ölçmə: Macrobenchmark `StartupTimingMetric`, profilli və profilsiz — rəqəm
   T2.6-nın açıq «ölçülmüş rəqəmlə» bəndini də bağlayır.

### Qəbul kriteriyası

- [ ] `app/src/main/generated/baselineProfiles/` repo-dadır
- [ ] Soyuq başlanğıc profilsiz varianta görə ən azı 15 % qısadır (rəqəm PR-da)
- [ ] Release APK büdcədədir (`apk-budcesi.js`)
- [ ] Profil generasiyası CI-da **işləmir** (yalnız lokal / əl ilə) — CI vaxtı artmır

## T6.6 — Tərəqqinin ixracı və idxalı

**P2 · 1 gün · Branch:** `feature/tereqqi-ixraci` · **Asılılıq:** T5.1

Android yedəyi (backup qaydaları, PR #16) eyni Google hesabı daxilində işləyir;
hesabsız cihaz və ya əl ilə köçürmə üçün yol yoxdur.

- Tənzimləmələr → «Tərəqqini ixrac et» / «idxal et» — Storage Access Framework,
  icazə tələb etmir.
- Format: versiyalı JSON (`{"versiya": 1, "tereqqi": …, "sehvler": …,
  "isareler": …, "qeydler": …}`).
- İdxal **birləşdirir** (çoxluqların birləşməsi), üzərinə yazmır; naməlum ID-lər
  atılır və sayı göstərilir.

Qəbul: ixrac → tətbiqi sil → idxal eyni tərəqqini verir (cihaz testi); zədəli
və ya gələcək versiyalı fayl izahlı xəta verir, mövcud data toxunulmur.

## T6.10 — «Tərcümə səhvi bildir»

**P1 · 0,5 gün · Branch:** `feature/terceume-sehvi-bildir`

### Problem

`qa-en.md`, `qa-tr.md`, `qa-ru.md` — üçündə də «ikinci oxucunun imzası
gözlənilir». Dalğa 3 – 5 daha 11 dil gətirir; hər biri üçün ana dili daşıyıcısı
tapmaq tək developer üçün real deyil. Avtomatik yoxlamalar (struktur, lüğət,
kodun skeleti, kompilyasiya) mənanı yoxlamır. Deməli tərcümə səhvlərini
istifadəçilər tapacaq — onlara bunu bildirməyin **bir toxunuşluq** yolu
lazımdır. «Xəta bildir» artıq var, amma ümumidir: hansı blok, hansı dil —
yazılmır.

### Addımlar

1. Baza dildən (`az`) fərqli dildə dərs bloku, çalışma və test sualının
   menyusunda (uzun basış / ⋮) «Tərcümə səhvi bildir».
2. Əvvəlcədən doldurulmuş GitHub issue açılır (mövcud «Xəta bildir»
   mexanizmi): başlıq `[<dil>] <blok id>`, gövdədə blok ID-si, dil, tətbiq
   versiyası, cari mətn (sitat) və «Düzgün variant:» sahəsi. Etiket: `tercume`.
3. Blok ID-si overlay açarıdır (T3.1) — issue-dan `localization/<dil>/*.json`
   sətrinə birbaşa getmək olur.
4. `.github/ISSUE_TEMPLATE/tercume.yml` — eyni sahələrlə, tətbiqdən kənar
   bildirişlər üçün.

### Qəbul kriteriyası

- [ ] Menyu bəndi yalnız baza olmayan dildə görünür
- [ ] Açılan issue-da dil, blok ID-si və cari mətn düzgündür (URL uzunluğu
      həddi: mətn 500 simvoldan sonra kəsilir)
- [ ] Brauzer yoxdursa tətbiq çökmür (mövcud «Xəta bildir» davranışı)
- [ ] `POLICY.md`-də axın yazılıb: issue → overlay düzəlişi → `build-locale` →
      növbəti release
- [ ] UI sətirləri bütün dillərdə

### Diqqət

Heç bir data avtomatik göndərilmir — istifadəçi issue-nu brauzerdə özü
göndərir. `PRIVACY.md` dəyişmir.
